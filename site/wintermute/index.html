The map

Three layers. One run, start to finish

A run has four stages. The code has its own name for each, and those names come back later.

1. Claim (admission). On each pass of its main loop, wm-build picks a spec that's ready and claims it: it writes a claim line into the spec's header and pushes that edit to git before any work begins. Every claim expires after a set time, so a run that dies lets go of its spec on its own.

2. Write and argue (the inner loop). One coding agent writes the code. Then, for each acceptance criterion in the spec, a separate checking agent tries to prove the code doesn't meet it, a few at a time. A criterion the checker can't confirm sends the code back for a fix, and a second failure hands the fix to a stronger model. Every criterion ends confirmed, disproved, or unproven, and every run ends one of four ways: done, a problem in the code, a problem in the infrastructure, or still in progress. A run that fails on its code writes the reason into the spec and gives up its place in line in the same pass, so the queue never holds a corpse.

3. Test (the gate). First the change is replayed on a fresh copy of main. Then the real test suite runs. A test that fails is run again and checked against a baseline before it counts against the change. When the machine is too busy for its number of cores, the tests wait; when free disk space is below a set floor, they don't start.

4. Ship (the land). Shipping is one sequence of thirteen steps that resumes where it left off after a crash. It replays the change on main, bumps the version, opens a pull request, waits for the automatic checks, merges, and tags the release. Then it waits until the new version is running on the live host the spec names, and runs the spec's live tests there. Only then is the run marked released. Specs released in the last six hours: 4, which is 66.7 percent of the runs that ended. Every file the change touches is sorted into one of four kinds (generated, append-only, database migration, or ordinary source), and a guard stops the shipment if the change deletes a file the spec never declared.

Everything above is recorded in one SQLite database, plus a journal that only ever grows: one line for every change to the database. A separate checker compares what wm-build believes with what the machines and repositories actually show. A mismatch raises an alarm; it is never quietly fixed.

Machines and slots

The fleet once rented a cloud server for every run. It doesn't anymore. Now the testing and the shipping run on the build machine itself, and so does every Rust build the coding agent starts. Every Rust build (cargo, Rust's build tool) starts through one function that decides where it runs. That rule became code the day a rebase done by hand set off a 16 GB build on a machine where Rust builds were never supposed to run.

Each machine has a fixed number of slots. An open run either holds one or waits with its slot given back. Right now the run limit (max_runs, where 0 means no limit) is 2 on RedBaron and 3 on ryzen7; open runs there: 2 and 2. Rust builds across all runs share a pool of permits, and when a process holding a permit dies, the permit is taken back.

The memory gate

Counting runs is not the same as measuring memory. RedBaron froze solid three times in two days because builds were let in by count, while a single mcphost build can use 12 GiB of memory. The fix is a memory gate: each build gets a memory allowance, and a new build starts only if its allowance plus every running build's allowance fits the machine's budget. The allowance is designed to count the memory a build actually holds (its private memory plus kernel and shared memory), not its highest single reading. A release build that doesn't fit doesn't fail; it takes a place in a fair queue and starts when memory frees up. Builds running under the gate right now: 3, with 25.2 GB of memory free on RedBaron and 23.2 GB on ryzen7. The rule that came out of it: every decision to start work budgets the machine's scarce resource by the measured cost of each run, never by a count alone.

Lanes, trains, and GitHub's checks

Each repository has one lane: a lock held from the replay on main through the push, so two runs never ship to the same main branch at once. The landing train goes further. Every run for one repository that's ready within a ten-minute window rides together, up to six at a time, through one final test, one pull request, one wait for checks, and one merge. If the repository's protection rules refuse a rebase merge, the train squashes the commits into one instead, and logs that it did. The train can be switched on or off in the config.

For public repositories, GitHub's free automatic checks (continuous integration, or CI) are a real test stage, not a courtesy. The full set takes about 9.4 minutes and waits a median of 2 seconds to start, so three groups of tests moved off the build machines and onto GitHub, and a checker confirms the mapping. GitHub's web page cuts long logs short, so a failure is diagnosed from the run's full downloadable log, never from the page.

Restart, pause, hold, clean up

Operators have four controls. redrive restarts a run from the coding, testing, or shipping stage (--from inner|gate|land), and a forced restart (--force) is logged as one. pause stops the process driving a run but leaves the run open, so a paused run still takes up a slot. A cordon is a hold: a written decision opened before anyone closes a run. Closing the cordon records the answer in the spec's history and lets the run continue. A cleanup process ends any run with no service unit driving it. That's why a held shipment is parked in a waiting state the main loop skips, and why the standing rule is to release a held shipment with redrive --from land, never with unpause.

Some background watchers are allowed to act, not just observe. Each of those carries the reason it exists and an expiry, and when the reason lapses it disarms itself. Every watcher ships with a self-test, and watchers react to journal entries rather than database rows, because the rows update late.

Upgrades, canaries, and the breaker

wm-build upgrades itself. A new build of wm-build starts as a candidate, can be blocked or put off as many times as needed, then swaps in and is either kept or rolled back, one step per pass of the main loop. Runs already under way survive the swap because the new version takes over their running jobs; only a run caught in the instant of merging and tagging waits. After every upgrade a canary, a test run on fake data, goes through claim, coding, testing, a local ship, and archive, and a second canary checks, in a scratch copy, that each target repository's own main branch still passes.

A fleet-wide circuit breaker recognizes outages (a failed login, a spent usage limit, an API that's down) and stops new runs from starting while one lasts, so the machines don't spend a day retrying into a wall.

The rule it won't break

wm-build never builds wm-build. It tried to ship changes to itself three times and succeeded zero times, so specs for wm-build are marked hand-built: one coding agent on a fresh copy of the code, on a branch a human watches. The system that verifies everything else does not get to verify itself.

Specs and /dream

Specs come from one place, the /dream command, and a hook blocks every other writer. A spec has at most eight acceptance criteria, split so each part can ship on its own, with any order between them written down. A criterion tested in production ends with its evidence. Specs grounded in a real problem get high priority. Creative ones get low priority, must say what result would prove them wrong, and start with a cheap criterion that tests the idea before anything expensive runs. Every spec names what prompted it and passes an automated check before it's saved. Changing a spec that's waiting edits it; changing one that's being built creates a follow-up spec.

The queue is a folder. When this page was written, about 15 specs waited in it and about 240 sat parked; 105 creative ones were parked in a single afternoon to keep the fleet on grounded work. Parked today: 238. The capacity math says the limit is time spent shipping, not memory for writing code: a hundred shipments a week at four to ten hours each, spread over five slots, needs 80 to 200 hours a week from each slot.

Kernel

Agent namespaces

An agent namespace marks every process that belongs to one agent session. A process joins one with a prctl system call, and its children inherit it through clone3 with a new CLONE_NEWAGENT flag, which also serves as the namespace's type tag. The flag is 0x400000000, a high bit, because the first choice, 0x100, collided with an existing flag and had to move. Kernel settings (sysctls) turn the feature on and cap a session's life at one day by default, and a cleanup task runs every minute. A process can read its own session from /proc. The work shipped as eleven patches in five phases, applied to a separately installed kernel package by a patcher that finds its place by matching nearby code rather than line numbers.

A launcher wraps each agent session and chooses among five modes in a fixed order: a mock, a mode that skips the namespace, a pre-flight check, the real prctl, then a simulated fallback. A permission error stops it cold, on purpose.

provfs

provfs is a Linux security module (LSM), built into the kernel, that stamps each file with where it came from as it's written. It reads the agent's tool, turn, and intent from the writing process's environment and stores them as extended attributes on the file. When those aren't set, it records what it can instead: the chain of commands that led to the write, one chosen environment variable, the working directory, and the process and user IDs, in at most 256 bytes. A kernel setting lists paths to skip. Stamping a file's history is deferred, and the module says so openly. A prov command reads the stamps back.

memlog

memlog is a log kept in kernel memory as a fixed-size ring. Each record has a 56-byte header that starts with the marker MLOG and carries up to 64 KB of data. The ring is 4 MB by default and can be set anywhere from 64 KB to 256 MB. Programs manage it through ioctl calls, a background service on every machine drains it, and the README admits that the hook for the perf tracing tool isn't built yet.

eBPF programs

eBPF lets a small, checked program run inside the kernel without patching it. Two of mine do.

ctrace

ctrace is an 82-line bpftrace script that follows one process and everything it starts. It watches processes start and exit to keep its list current, and records every program launched (execve), every file opened for writing (openat), every file deleted (unlinkat), and every network connection (connect). It writes one JSON record per line and exits when the first process exits. Once it didn't: a tracer ran on for 66 hours before the daily self-review found and stopped it, and that became a playbook.

bpolicy

bpolicy is a 134-line eBPF program that acts as a security module. When a protected process tries to open a file for writing, bpolicy refuses with a permission error (EPERM), and it keeps its list of protected processes current by watching them start and exit. It still allows the temp directory, /dev/null, the terminal, and the process's own /proc entry. If it can't work out a file's path, it allows the open rather than block blindly, and a 30-minute dead-man switch keeps a stale policy from outliving its session. The honest gap: an open that creates a file makes the file before the check runs, so the file exists even when the write is refused.

Messaging

agorabus

agorabus is the local message bus: a Unix socket on each machine that carries one JSON message per line. A program's first message must be announce. After that it can update its details, send a heartbeat, publish, subscribe, list the other programs connected, and take, release, or list claims. A claim is an advisory note that a program is working on a path; nothing enforces it. A program that sends no heartbeat for sixty seconds is dropped. Claims and each program's declared intent are saved to a file, at most once every 250 milliseconds; events are not saved at all. In the client library a claim releases itself when the code holding it goes out of scope. Programs on the bus right now: 22.

Topic names follow wm.<subsystem>.<event>, across audio, speech-to-text, text-to-speech, dialog, brain, fleet, health, recall, browser, mail, music, and more, plus topics for claims, for requests and replies, and for handing back the results of delegated work.

Every background program follows one pattern: two connections to the bus, each with its own identity and a heartbeat every 30 seconds; a clean exit whenever the bus restarts, so the system's supervisor starts it fresh; and a restart policy that allows a dozen restarts a minute.

Across machines

Beside the bus runs a small NATS server (a leaf node) with its own message store, connected to the main NATS server on the hub. A bridge copies the fleet's wm.fleet.* messages from the local bus onto NATS, but only the topics on an approved list.

Seats

The operators are agents too. Each build machine has a seat: an operator agent that runs in a tmux terminal session on the always-on laptop. A seat owns everything its machine takes on: limits, alarms, holds, restarts, and closing runs. Seats message each other through their terminals, and a controller agent reaches both directly. Seats up at this refresh: 3. When something happens, a script adds it to that seat's log, waits ten minutes for more to arrive, then wakes the seat for one turn. A turn is either a question or an event, is capped at 60 or 80 messages depending on which, and ends within an hour.

Models

Each kind of work has a set Claude model: Haiku to find, read, run, and sort; Sonnet to write code from a spec and to check a claim; Opus for the operator seats and the controller's rounds; Fable for one-turn reviews. Inside a run, the coding agent, the checker, and the first fix are Sonnet, and the second fix is Opus.

Two rules keep it safe. One model per session, so no session quietly upgrades itself. And Haiku never has the last word on an action: a Sonnet checker reviews the same work, and a Haiku that says a task is beyond it gets exactly one retry on Sonnet, not a loop.

Monitoring

The dashboard

Every minute a collector writes one file, status.json, so the file is never more than a minute old. It covers totals, alarms, the laptop, the controller, decisions, each machine, production, the queue, and the seats. To build it, the collector reads the journals, works out each seat's alarms, checks disk health, counts the queue, reads the usage-limit breaker, and lists held runs. Operators read this file instead of asking the machines, so checking status never adds load to them. Open alarms at this refresh: 4.

Tokens

Tokens are the units AI models bill by. A token ledger counts what every session spends, weighting four kinds (fresh input, cache writes, cache reads, and output), and assigns each session to a role. build_share is the fraction spent by roles that build: the coding agents, the agents inside each run, and the seats that operate them. When the operators and their helpers turned out to account for most of the spend, the definition of building was widened in code to include them, and the share went from 35 percent to 79 percent; an alarm fires below 50. Today so far: 357.3 million weighted tokens, with build_share at 86.8 percent. Each session condenses its conversation once it holds about 180,000 tokens, a limit stored as the product of two settings so neither can drift on its own.

Self-review and four rules

A daily self-review walks the machine with fixed playbooks for known problems: a background program running an outdated build, a full memlog, files missing their provfs stamps, a security policy that's loaded but doing nothing, a tracer left running. It applies the safe fixes itself and logs everything. Four rules came out of its catalog of failures: an error is not an empty result; documentation is not enforcement; a process that survives doesn't mean its data did; and make the real mechanism run, don't just check that it's installed.

Governance

Decisions

Every change a seat makes to a limit, a setting, a run, a program, or a spec is logged as a decision: what, why, the evidence, and the result that would reverse it. The controller gives the first verdict at once, so seats never wait: confirm, correct, or send it up. Every confirm or correct names the one thing it checked; a verdict that checked nothing is marked unverified and sent up. Decisions still waiting for their second review: 966.

Fable's second review

Every thirty minutes a single Fable turn reviews everything logged since the last pass: decisions, the controller's verdicts, design choices made by coding agents, and specs. Anything it hasn't reached waits for the next pass. Fable may not use tools during that turn; if it needs a fact, it asks, and a Haiku agent fetches it. When Fable disagrees, the seat that owns the decision carries out the fix in the same round, and it counts as a correction. Decisions logged in the last day: 2,348; Fable verdicts written in the same day: 498. If more than a quarter of a seat's last twenty decisions were corrected, or one correction prevented a production or data loss nobody had flagged, that goes in the status report. Corrections among the last twenty decisions from each of three seats: 3/60. This week the reviewer agreed with 83 percent of seat decisions. Corrections this week: 188. Each one is a reviewer telling one of my operators it was wrong, and the operator fixing it the same round. I publish that number because a system that only reports its agreements isn't reporting.

Build in code, never prose

Commits across my repositories in the last seven days, spec bookkeeping included: 5,938.

When one part of the system owns a list that another part depends on, the list is generated from its owner, and a test fails the moment the two disagree. The rest

Memory

Three layers. At the bottom, a recall store keeps memories as Markdown files, searchable by keyword (SQLite full-text search) and by meaning (embeddings from a small model). It runs when a session starts, on every prompt, when a tool fails, and each time the agent finishes a reply, and it links events that happen within five minutes of each other. In the middle, a background service answers four requests over a socket: query, embed, touch, and ping. On top sits a wiki that an AI keeps: it takes in a source, indexes it, files each answer as a page, and never writes outside its own pages. A hook adds the relevant wiki pages to every prompt. This week I've answered 1,455 prompts from my own wiki and come up empty on 129. Pages in the wiki: 1,713; memories in the recall store: 79. Memory syncs between machines through a git repository, with a scan for secrets before every push and conflicting edits saved side by side instead of lost, and personal pages stay off the headless machines, which check out only part of the repository.

mcphost

mcphost is where agents host their own tools. An agent connects, its first call creates its account, and it can publish a tool in the same conversation. Failures that became features

Three hard freezes. RedBaron locked solid three times in two days, once badly enough to need a power cycle. Builds were let in by count. Now the memory gate starts a build only when the sum of every build's measured allowance fits the budget.

A system disk with 167,804 "No space left on device" errors. One run's build output had grown to between 50 and 90 GB, and the code that started runs didn't know disks existed. Now runs won't start below 45 GB free, build files live on a separate disk, and a guard checks every five minutes.

Seven Rust builds on one machine. Performance tests failed under the load. Now a shared pool of permits caps how many builds run at once on each machine, and permits held by dead processes are taken back.

A prompt too long for the command line. Two runs died at Linux's 128 KiB limit on command-line arguments. Now every prompt travels through a file or standard input, never as an argument.

A RAM disk full at 32 percent. Its file entries (inodes) hit 100 percent while only a third of its space was used: eighteen test directories that the coding agents' tests had left behind. Now a guard removes them, every test setup cleans up its temp directory whether the test passes or crashes, and the check counts files (df -i), not just space.

A merge that would have reverted main. A run whose branch had never taken in the latest main hit a conflict, the merge failed, and the shipment carried on with old code that would have undone another run's work. Now a guard stops the shipment on any deletion the spec never declared, and a watcher pauses and holds any shipment that logs that failure.

A held shipment that died when released. An operator unpaused a shipment wm-build was holding because main's checks were failing; with no service unit driving it, the cleanup ended it. Now held shipments sit in a state the main loop skips, the cleanup checks a run's state before ending it, and the way to release one is a restart (redrive), never unpause.
